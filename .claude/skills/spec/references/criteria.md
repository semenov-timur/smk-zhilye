# Как писать критерии приёмки

Критерий приёмки — это утверждение, про которое можно однозначно сказать
«выполнено» или «нет». Из него напрямую получается тест или проверка.

## Правила

1. **Одно утверждение — один критерий.** «Форма валидирует телефон и
   отправляет письмо» — это два критерия.
2. **Наблюдаемый результат, а не реализация.** Не «используется хук
   afterChange», а «после создания заявки на адрес из настроек приходит письмо».
3. **Без оценочных слов.** «Быстро», «удобно», «красиво», «корректно» —
   не проверяются. Заменяй числами и фактами: «Lighthouse Performance ≥ 90
   на мобильном профиле», «на 360 px нет горизонтальной прокрутки».
4. **Краевые случаи — отдельными критериями.** Пустые поля, ошибка сети,
   нет прав, нет данных.
5. **Способ проверки в скобках:** `(test)`, `(e2e)`, `(visual)`, `(manual)`.
   `manual` — только если автоматизировать неразумно; опиши, как проверять.

## Формат

Обычно хватает одной фразы. Для сложного поведения можно «Дано / Когда / Тогда»:

```
AC-4: Дано: письмо не отправилось из-за ошибки SMTP.
      Когда: посетитель отправляет форму.
      Тогда: заявка сохранена в админке, посетитель видит «Спасибо»,
      ошибка записана в лог. (test)
```

## Плохо → хорошо

| Плохо | Хорошо |
|---|---|
| Форма работает корректно | AC-1: Заполненная форма создаёт запись в коллекции `leads` (e2e) |
| Телефон валидируется | AC-2: Номер не в формате +7XXXXXXXXXX или 8XXXXXXXXXX — ошибка «Проверьте номер телефона» под полем, отправка не происходит (e2e) |
| Удобно на телефоне | AC-3: На ширине 360 px форма без горизонтальной прокрутки, поля и кнопка не меньше 44 px по высоте (visual) |
| Данные защищены | AC-4: Анонимный `GET /api/leads` возвращает 403 (test) |
| Страница быстрая | AC-5: Lighthouse Performance ≥ 90, мобильный профиль, главная (manual) |
| Красивый дизайн | Не критерий. Дизайн согласуется по макетам, критерий — «соответствует макету X» (visual) |

## Сколько критериев

Обычно 4–10. Больше 12 — признак, что изменение стоит разбить.
