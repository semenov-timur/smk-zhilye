# Скилл spec: изменения через спецификации

Процесс: **new → plan → apply → verify → archive**. Между шагами — остановка
и явное подтверждение пользователя. Цель — чтобы агент делал именно то,
о чём договорились, а пользователь контролировал результат в трёх точках:
спецификация, план, готовая работа.

## Где что лежит

```
docs/changes/NNN-slug/change.md   — что и зачем (пишет пользователь, агент помогает)
docs/changes/NNN-slug/tasks.md    — план (пишет агент, утверждает пользователь)
docs/changes/NNN-slug/verify.md   — отчёт о проверке (пишет агент)
docs/changes/archive/             — выполненные изменения
docs/specs/<область>.md           — как система работает сейчас
```

Шаблоны: `templates/`. Как писать критерии приёмки: `references/criteria.md`.

## Статусы

Статус хранится во frontmatter `change.md` (поле `status`):

| Статус | Значит | Кто переводит |
|---|---|---|
| `draft` | Черновик, обсуждаем | агент при создании |
| `approved` | Спецификация утверждена | агент, только после явного «утверждаю» пользователя |
| `planned` | План утверждён, можно реализовывать | агент, только после явного «утверждаю» к плану |
| `in-progress` | Идёт реализация | агент в начале apply |
| `review` | Реализовано, ждёт проверки пользователем | агент после verify без ❌ |
| `blocked` | Остановлено, нужен ответ пользователя | агент, с причиной в поле `blocked_reason` |
| `archived` | Выполнено и перенесено в архив | агент в archive |

Никогда не перескакивай статусы и не ставь `approved`/`planned` без явного
согласия. «Ок», «да», «утверждаю», «го» в ответ на твой прямой вопрос
об утверждении — это согласие. Молчание или правки — нет.

## Определи режим

| Пользователь говорит | Режим |
|---|---|
| «новая спека …», «давай опишем фичу …», «хочу сделать …» | new |
| «спланируй NNN», «составь план», «обнови план NNN» | plan |
| «реализуй NNN», «делай NNN», «продолжи NNN» | apply |
| «проверь NNN» | verify |
| «архивируй NNN», «закрываем NNN» | archive |
| «статус», «что в работе» | status |

Если номер не назван и в работе одно изменение — бери его. Если несколько —
спроси, какое.

## Режим new — создать изменение

1. Прочитай `docs/product.md`, `docs/architecture.md`, связанные файлы
   в `docs/specs/` и `docs/decisions/`. Если в `docs/changes/` уже есть
   изменение на эту тему — скажи об этом и спроси, продолжаем его или новое.
2. Задай пользователю **3–7 уточняющих вопросов** одним сообщением.
   Спрашивай то, без чего нельзя написать проверяемые критерии: поведение
   в краевых случаях, что видит пользователь, куда идут данные, что точно
   не входит. Не спрашивай то, что уже есть в документах.
3. Номер — следующий после максимального среди `docs/changes/*` и
   `docs/changes/archive/*`, три цифры. Slug — 2–4 английских слова через дефис.
4. Создай `docs/changes/NNN-slug/change.md` по `templates/change.md`,
   статус `draft`.
5. Правила содержания:
   - Требования — только из ответов пользователя и документов. Ничего не
     придумывай. Если чего-то не хватает — запиши в «Открытые вопросы».
   - Критерии приёмки по `references/criteria.md`: номер `AC-N`, одно
     проверяемое утверждение, способ проверки в скобках.
   - Раздел «Не входит» обязателен.
   - Изменение помещается примерно на одну страницу. Больше — предложи
     разбить на несколько.
6. Покажи краткое содержание и открытые вопросы, спроси:
   «Утверждаете спецификацию или правим?». Код не пиши.
7. После явного согласия — статус `approved`.

## Режим plan — составить план

Только для изменения со статусом `approved`.

1. Прочитай `change.md`, связанные `docs/specs/`, `CLAUDE.md` и **изучи
   существующий код**, который затронет изменение.
2. Создай `tasks.md` по `templates/tasks.md`:
   - Шаги по 15–60 минут работы, в порядке выполнения, у каждого — что
     сделать, какие файлы, какой результат.
   - Матрица покрытия: каждый `AC-N` → чем будет подтверждён (тест с именем
     файла, e2e-сценарий, скриншот, ручная проверка). Критерий без способа
     проверки — недопустим.
   - Новые зависимости, переменные окружения, миграции — отдельными пунктами
     с обоснованием.
   - Риски и открытые вопросы. Если нашёл противоречие в `change.md` —
     запиши здесь, не исправляй спецификацию сам.
3. Код не пиши. Покажи план кратко: число шагов, ключевые решения,
   открытые вопросы. Спроси: «Утверждаете план?».
4. После явного согласия — статус `planned`.

**Перепланирование.** Если пользователь изменил `change.md` после утверждения
плана (или apply остановился из-за неверного плана), обнови `tasks.md`:
выполненные шаги `[x]` сохрани, остальные пересобери, покажи разницу и снова
попроси утвердить. На время пересогласования статус — `approved`.

## Режим apply — реализовать

Только для изменения со статусом `planned` или `in-progress`.

1. Убедись, что рабочее дерево чистое. Обнови `develop`
   (`git switch develop && git pull`, pull — если настроен remote) и создай от него ветку
   `change/NNN-slug`; если ветка уже есть — переключись на неё и при
   необходимости сделай `git rebase develop`. Статус → `in-progress`.
   Правила веток и коммитов — `docs/git-workflow.md`.
2. Выполняй шаги `tasks.md` **по порядку**:
   - один шаг — один коммит в формате Conventional Commits: тип и область
     на английском, описание на русском (`feat(leads): добавить поле согласия`);
   - после шага отметь его `[x]` в `tasks.md`;
   - тесты пиши вместе с кодом, в названии теста — номер критерия.
3. После каждых 2–3 шагов запускай линтер, проверку типов и тесты.
   Красное — чини сразу, не копи.
4. **Остановись и спроси**, если:
   - план оказался неверным или нужен шаг, которого в плане нет
     (больше мелкой вспомогательной правки);
   - требование в `change.md` невозможно или противоречиво выполнить;
   - нужна новая зависимость, не указанная в плане;
   - тест не проходит и причина — в требованиях, а не в коде.
   При остановке: статус `blocked`, причина в `blocked_reason`, короткий
   вопрос пользователю. Не обходи проблему молча.
5. Когда все шаги выполнены — переходи к verify.

Никогда: не коммить и не пушь в `main` и `develop`, не мерджи PR, не делай
force push в общие ветки, не удаляй и не ослабляй тесты ради зелёного
прогона, не правь `change.md`.

## Режим verify — проверить

1. Запусти всё: линтер, типы, тесты, сборку, e2e. Сохрани итог.
2. Для визуальных критериев сделай скриншоты (Playwright) на 360 px и
   1280 px, положи в `docs/changes/NNN-slug/screenshots/`.
3. Заполни `verify.md` по `templates/verify.md`: каждый `AC-N` → чем
   подтверждён → статус:
   - ✅ подтверждён (тест прошёл, есть скриншот, проверено вручную с описанием как);
   - ❌ не выполнен или тест падает;
   - ⚠️ нельзя проверить автоматически — нужна проверка пользователем
     (опиши, что именно посмотреть).
4. Будь честен: критерий без доказательства — не ✅. Не подменяй
   проверку требования проверкой «код написан».
5. Есть ❌ — вернись в apply или остановись с вопросом. Нет ❌ — статус
   `review`, покажи пользователю сводку, список ⚠️ для ручной проверки и
   что посмотреть в браузере.

## Режим archive — закрыть

Только после явного «ок» пользователя по результатам verify.

1. Обнови `docs/specs/<область>.md` (создай по `templates/area-spec.md`,
   если нет): впиши итоговое поведение системы — требования, которые теперь
   истинны. Описывай, как работает система, а не историю изменения.
   В конце файла — ссылка на изменение в архиве.
2. Если поменялись команды, переменные окружения или структура — обнови
   `README.md`, `CLAUDE.md`, `docs/architecture.md`.
3. Если было принято архитектурное решение — предложи запись в `docs/decisions/`.
4. Добавь строку в `CHANGELOG.md`, раздел «Не выпущено», в подраздел
   «Добавлено», «Изменено» или «Исправлено»: что получил пользователь сайта
   или менеджер, одной фразой, с номером изменения.
5. Статус `archived`, перенеси папку в
   `docs/changes/archive/ГГГГ-ММ-ДД-NNN-slug/`.
6. Закоммить (`docs(changes): archive NNN-slug`), запушь ветку и подготовь
   PR в `develop`: название `feat(<область>): <итог> (#NNN)`, в описании —
   ссылка на `change.md`, итог `verify.md`, что проверить руками. Если есть
   доступ к GitHub/GitLab CLI — открой PR, иначе выведи текст для вставки.
   Мерджит пользователь (squash merge).

## Режим status

Пройди по `docs/changes/*/change.md`, выведи таблицу: номер, название,
статус, следующий шаг. Отдельно — заблокированные с причиной.

## Общие правила

- Пиши документы по-русски, коротко, без воды. Конкретика: числа, имена
  полей, адреса страниц.
- Мелкие правки (текст, опечатка, цвет одного элемента) не требуют
  изменения: делай их в ветке `fix/описание` от `develop` и предлагай PR.
- Не держи в голове то, что можно записать: решения, вопросы и отклонения
  фиксируй в файлах изменения.
