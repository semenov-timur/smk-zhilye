# CLAUDE.md — правила проекта

Сайт строительной компании ООО СМК «Жильё». Разработчик — один человек,
сильный в бэкенде (Java, Go), во фронтенде начинающий. Объясняй решения
во фронтенде коротко и по делу, когда это помогает понять код.

## Обязательно прочитать перед работой

- `docs/product.md` — что делаем, для кого, что в каком этапе.
- `docs/architecture.md` — стек, модель данных, принципы.
- `docs/decisions/` — принятые решения. Не противоречь им молча.
- `docs/git-workflow.md` — ветки, коммиты, PR, релизы.
- `docs/design-system.md` — для любой вёрстки. Если раздел не заполнен,
  не придумывай фирменный стиль: используй нейтральные заглушки и скажи об этом.

## Стек

TypeScript (strict) · Astro в режиме SSR · Payload 3 · PostgreSQL ·
Tailwind CSS · Vitest · Playwright · Docker Compose. Node.js 26 LTS, pnpm 12.21
(workspaces: `apps/cms`, `apps/site`). Точные версии — в `package.json`
и `pnpm-lock.yaml`, новые зависимости ставятся без `^`.

## Процесс

- Заметные задачи — только через скилл `spec`: изменение в `docs/changes/NNN-slug/`
  → план → реализация → проверка → архив. Мелкие правки (текст, опечатка,
  один стиль) — без спецификации, но в ветке `fix/описание` и через PR.
- Не начинай реализацию, пока у изменения нет статуса `planned`
  (план утверждён пользователем).
- `change.md` меняет только пользователь. Нашёл противоречие или пробел —
  запиши в «Открытые вопросы» плана и спроси, а не решай сам.
- Одна задача из `tasks.md` — один осмысленный коммит.

## Git

Полные правила — `docs/git-workflow.md`. Коротко:

- Постоянные ветки: `main` — продакшен (только релизы), `develop` — интеграция,
  ветка по умолчанию.
- Изменение — ветка `change/NNN-slug` от свежего `develop`; мелкая правка без
  спецификации — `fix/описание` от `develop`. Перед созданием ветки:
  `git switch develop && git pull` (pull — если настроен remote),
  рабочее дерево должно быть чистым.
- Коммиты — Conventional Commits: тип и область на английском, описание
  (заголовок после двоеточия и тело) — на русском:
  `feat(leads): добавить чекбокс согласия в форму заявки`.
- PR — только в `develop`. Название `feat(<область>): <итог по-русски> (#NNN)`, в описании —
  ссылка на `change.md`, итог `verify.md`, что проверить руками.
- **Мерджит только пользователь.** Агент не мерджит PR, не коммитит и не пушит
  в `main` и `develop`, не ставит теги, не делает force push в общие ветки,
  не удаляет ветки, не переписывает историю `main` и `develop`.
- В своей ветке `change/*` можно `rebase` на `develop` и `push --force-with-lease`.
- Релиз и hotfix — только по явной просьбе пользователя и строго по разделам
  «Релиз» и «Срочное исправление» в `docs/git-workflow.md`.
- При архивации изменения добавь строку в `CHANGELOG.md`, раздел «Не выпущено».

## Код

- Идентификаторы и имена файлов — на английском. Документация, описания
  коммитов, тексты интерфейса и комментарии к бизнес-логике — на русском.
- TypeScript strict, без `any` без крайней необходимости (тогда — с комментарием почему).
- Контент страниц — только из Payload. Захардкоженные тексты допустимы лишь
  для служебных подписей интерфейса.
- Новая npm-зависимость — только с обоснованием в плане.
- Секреты — только через переменные окружения; новые переменные добавляй
  в `.env.example` с комментарием.
- Шрифты и скрипты — локально, без Google Fonts и зарубежных CDN.
- Формы с персональными данными: обязательный чекбокс согласия со ссылкой
  на политику, время согласия сохраняется вместе с заявкой.

## Тесты

- Тесты, закрывающие критерий приёмки, содержат его номер в названии:
  `it('AC-3: anonymous GET /api/leads returns 403', ...)`.
- Права доступа и хуки Payload — интеграционные тесты (Vitest).
- Пользовательские сценарии — e2e (Playwright), проверка на ширине 360 px и 1280 px.
- Не ослабляй и не удаляй тест, чтобы он прошёл. Если тест неверен — скажи об этом.

## Определение готовности задачи

1. Линтер, проверка типов, тесты и сборка проходят.
2. Все критерии приёмки изменения подтверждены в `verify.md`.
3. Документация обновлена, если поменялось поведение или команды.

## Команды

Из корня репозитория. Подробнее — `README.md`.

| Команда | Что делает |
|---|---|
| `cp .env.example .env` | Создать локальный `.env` |
| `docker compose up` (`pnpm dev`) | Postgres, CMS на :3000, сайт на :4321 |
| `pnpm install` | Зависимости на хосте (для проверок) |
| `docker compose up -d postgres` | Только база — нужна для `test` и `test:e2e` |
| `pnpm lint` / `pnpm format:check` | ESLint / Prettier |
| `pnpm typecheck` | `tsc` в cms, `astro check` в site |
| `pnpm test` | Vitest (apps/cms) |
| `pnpm build` | Сборка обоих приложений |
| `pnpm test:e2e` | Playwright (apps/site), после `pnpm build` |
| `pnpm --filter cms generate:types` | Обновить типы Payload |
| `pnpm --filter cms payload migrate:create <имя>` | Миграция после изменения коллекций |
