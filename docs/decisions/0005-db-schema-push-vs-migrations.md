# 0005. Схема базы: push в dev, миграции в production, отдельная база для e2e

Дата: 2026-11-17 · Статус: принято

## Контекст
Payload с адаптером PostgreSQL умеет два режима. В dev (`next dev`, Vitest) он сам
приводит схему базы к коллекциям (push). В production схема меняется только
миграциями. Если CMS в production-режиме запустить на базе, где работал push,
Payload останавливается с интерактивным вопросом о потере данных. Так зависал e2e
в изменении 001.

## Решение
- Локальная разработка и Vitest работают с основной базой (`POSTGRES_DB`) в режиме push.
- Production и e2e применяют миграции из `apps/cms/src/migrations/` при старте
  (`prodMigrations`).
- e2e использует отдельную базу `<POSTGRES_DB>_e2e`. Её создаёт
  `docker/postgres/init-e2e-db.sh` при первом запуске Postgres, в CI — шаг workflow.
- Изменил коллекции — создай миграцию:
  `pnpm --filter cms payload migrate:create <имя>`.

## Почему
- Push даёт быстрый цикл в разработке: поменял поле — сразу видно в админке.
- e2e в CI собирает CMS в production-режиме, поэтому забытая миграция ломает CI,
  а не боевой сайт.
- Отдельная база для e2e не смешивает два режима в одной схеме.

## Альтернативы
- Только миграции и в dev — надёжнее, но каждое изменение коллекции требует миграции
  ещё до проверки в админке.
- Одна база для всего — e2e зависает на вопросе Payload.
- Поднимать базу из тестов (testcontainers) — лишняя зависимость. От неё отказались
  при планировании 001.

## Когда пересмотреть
Если появятся тесты, которые пишут данные, — завести отдельную базу и для Vitest.
