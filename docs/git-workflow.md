# Как ведём git-репозиторий

Упрощённый Git Flow для одного разработчика и ИИ-агента:
постоянные ветки `main` и `develop`, короткие ветки под каждое изменение,
релиз — это PR из `develop` в `main` с тегом.

## Ветки

```
main      ──●────────────────●──────────●──   продакшен: только релизы с тегами
             \              / \        /
develop       ●──●────●────●───●──●───●────   интеграция, тестовый стенд
               \   /    \  /     \  /
change/…        ●●      ●●       ●●           одно изменение из docs/changes
```

| Ветка | Создаётся от | Вливается в | Назначение |
|---|---|---|---|
| `main` | — | — | Боевой сайт. Каждый мердж сюда — релиз с тегом `vX.Y.Z`. |
| `develop` | `main` | `main` (PR «Release vX.Y.Z») | Готовые, но не выпущенные изменения. Ветка по умолчанию, автодеплой на тестовый стенд (когда он появится). |
| `change/NNN-slug` | `develop` | `develop` | Одно изменение. Имя = папка в `docs/changes/`. |
| `fix/описание` | `develop` | `develop` | Мелкая правка без спецификации (текст, опечатка, стиль). |
| `hotfix/описание` | `main` | `main` и `develop` | Срочное исправление боевого сайта. |
| `release/X.Y` | `develop` | `main` и `develop` | Только по необходимости — см. «Релизная ветка». |

Имена веток — латиница, нижний регистр, слова через дефис:
`change/005-lead-form`, `fix/footer-phone`, `hotfix/form-500`.

## Защита веток (настроить в GitHub/GitLab)

- `main` и `develop`: прямые пуши запрещены, только через PR / MR.
- Мердж только при зелёном CI.
- Force push и удаление этих веток запрещены.
- Ветка по умолчанию — `develop`.

## Коммиты

Формат [Conventional Commits](https://www.conventionalcommits.org/ru/):
тип и область — на английском, описание (заголовок после двоеточия и тело
коммита) — на русском.

```
<тип>(<область>): <что сделано>

feat(leads): добавить чекбокс согласия в форму заявки
fix(site): исправить ссылку на телефон в подвале
docs(changes): архивировать 005-lead-form
chore(deps): обновить astro до 6.x
test(cms): покрыть тестами права доступа к заявкам
refactor(site): вынести компонент ProjectCard
```

Типы: `feat` — новая возможность, `fix` — исправление, `docs`, `test`,
`refactor`, `chore` (инфраструктура, зависимости, конфиги), `style` (форматирование).
Область — `site`, `cms`, `infra`, `leads`, `deps` и т.п.

Один коммит — один логичный шаг. В ветке изменения это один шаг из `tasks.md`.

## Цикл одного изменения

```bash
git switch develop && git pull
git switch -c change/005-lead-form
# … работа по tasks.md, коммит на каждый шаг …
git push -u origin change/005-lead-form
# открыть PR: change/005-lead-form → develop
```

- Название PR: `feat(leads): форма заявки с уведомлениями (#005)`.
- В описании PR: ссылка на `docs/changes/…/change.md`, краткий итог из `verify.md`,
  что проверить руками.
- **Мердж в `develop` — squash merge**: вся ветка становится одним коммитом
  с названием PR. Подробная история изменения остаётся в `docs/changes/archive/`.
- После мерджа ветку удаляем.
- Если `develop` ушёл вперёд — `git rebase develop` в своей ветке
  (она личная, переписывать её историю можно), затем `git push --force-with-lease`.

## Релиз

Релиз — когда в `develop` накопилось то, что нужно выкатить на боевой сайт.

1. Убедиться, что CI на `develop` зелёный и на тестовом стенде всё работает.
2. В `CHANGELOG.md` переименовать раздел «Не выпущено» в `## [X.Y.Z] — ГГГГ-ММ-ДД`
   и добавить над ним новый пустой «Не выпущено». Закоммитить в `develop` через
   короткую ветку `chore/release-X.Y.Z` или прямо в PR релиза.
3. PR `develop → main` с названием `Release vX.Y.Z`, в описании — раздел из CHANGELOG.
4. **Мердж в `main` — merge commit** (не squash), чтобы границы релизов были видны.
5. Тег на коммит мерджа и пуш тега:
   ```bash
   git switch main && git pull
   git tag -a vX.Y.Z -m "Release vX.Y.Z"
   git push origin vX.Y.Z
   ```
6. Деплой на продакшен (после настройки CI/CD — автоматически по тегу).

### Версии

[SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`.

- До запуска сайта — `0.x.y`: `0.1.0`, `0.2.0`… каждый заметный этап — новый MINOR.
- Первый публичный запуск — `1.0.0`.
- После запуска: новые возможности — MINOR (`1.1.0`), исправления — PATCH (`1.1.1`),
  несовместимые изменения (смена структуры URL, переезд) — MAJOR.

## Срочное исправление (hotfix)

Когда на боевом сайте баг, а в `develop` лежит невыпущенное:

```bash
git switch main && git pull
git switch -c hotfix/form-500
# исправление + тест
# PR hotfix/form-500 → main (merge commit), тег vX.Y.(Z+1)
# затем влить main в develop, чтобы исправление не потерялось:
git switch develop && git pull && git merge main && git push
```

## Релизная ветка — только когда нужна

Если релиз нужно стабилизировать несколько дней (например, заказчик принимает
версию, а параллельно идёт работа над следующим этапом):

```bash
git switch develop && git pull
git switch -c release/1.0
```

В `release/1.0` — только исправления по замечаниям. Когда версия принята:
PR `release/1.0 → main`, тег, затем `release/1.0` вливается в `develop`.
Новые фичи тем временем продолжают идти в `develop`.

## Что может и чего не может ИИ-агент

Может: создавать ветки `change/*` и `fix/*` от `develop`, коммитить в них,
пушить их, готовить описание PR и CHANGELOG.

Не может без явной просьбы пользователя: мерджить PR, коммитить или пушить
в `main` и `develop`, создавать теги, делать force push в общие ветки,
удалять ветки, переписывать историю `main` и `develop`.

## Шпаргалка

| Задача | Команда |
|---|---|
| Начать изменение | `git switch develop && git pull && git switch -c change/NNN-slug` |
| Обновить ветку от develop | `git fetch && git rebase origin/develop` |
| Запушить после rebase | `git push --force-with-lease` |
| Посмотреть, что войдёт в релиз | `git log main..develop --oneline` |
| Поставить тег | `git tag -a vX.Y.Z -m "Release vX.Y.Z" && git push origin vX.Y.Z` |
